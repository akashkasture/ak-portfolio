Trace

The portfolio is one request, moving through an engineer's system, observed.

Five metaphors were evaluated. The winner is not a place — not a universe, not a city. It is a distributed trace: the artefact engineers already use to understand a system they cannot see.

It wins on one structural argument. Every other candidate carries either space or time. A trace carries both, natively, which is the only reason Experience, Projects, Skills and GitHub can live in one geometry without being forced.

01 · The question

Why the solar system fails, precisely

It isn't that the solar system is unrelated to software. It's that its structure encodes nothing.

A visual metaphor is doing its job when moving an object changes what the page claims. In the solar system, position is orbital radius — arbitrary. Size is arbitrary. Orbital period is arbitrary. You can shuffle every planet and lose no information, which is the proof that none was there. It is a backdrop that happens to be 3D.

So the bar for the replacement isn't "more relevant." It's load-bearing geometry: every axis must carry meaning, so that the scene is not an illustration of the portfolio but a reading of it.

The test applied throughout

If an object can be moved without making the page say something different, the axis it moved along is decoration. Delete the axis, or give it a job.

Why each of the others loses

"Core, services, nodes, streams" is the solar system with the nouns swapped. Nothing constrains where a thing sits, so nothing is claimed. It fails the same test the incumbent fails.

Rejected
Digital city

The most common "impressive 3D portfolio" there is. A project is not shaped like a tower, so the mapping is costume. It scales badly — a new project means a new building — and it is the heaviest option to build, texture and ship, for the least meaning per polygon.

Absorbed, not rejected
Architecture world

Genuinely strong, and already half-built here as Signal Flow. Its ceiling is that a topology has no time axis, so career progression never fits — a timeline is not a layer. Trace keeps this entirely and adds the missing dimension.

Rejected
Commit graph

Real, and native to the GitHub section. But a DAG expresses history and nothing else — architecture and skills have to be bolted on. Strong for one section, thin as the whole world.

03 · Design concept

The portfolio is a trace

One request enters the system. It fans out across services, spends time in each, emits events, and returns. Reading that trace is how an engineer understands a system they cannot see directly — and it is how a visitor will understand this engineer.

The choice is not decorative. A trace is a first-class engineering artefact, not a metaphor borrowed from astronomy or urban planning. Zipkin is already listed on the gateway node of the existing graph — this is Akash's own instrumentation turned on his own career.

And the vocabulary maps without strain, because the interactions the brief asks for are things a trace viewer already does:

  • Span attributes. Every span carries key–value tags. "Click a technology, highlight every project that used it" is not a feature to invent — it is attribute filtering, which is what the primitive is for.
  • Span events. Timestamped points inside a span. That is exactly a commit.
  • Annotations. Notes attached to a span at a moment. That is exactly a blog post.
  • The critical path. The chain of spans that determined the total duration — and, read the other way, the decisions that actually shaped a career.
The one real risk

A trace is an analytical object. Read carelessly it can feel clinical, and "trace" carries a whiff of debugging — of something having gone wrong. Two mitigations, both structural rather than cosmetic: the frame is observability, not incident response — the language throughout is "read the system", never "diagnose the fault"; and the warmth is carried by the writing in the panels, which is where a portfolio's voice belongs anyway.

The second risk is looking like a Gantt chart. That is a real failure mode and it is guarded against in §04: if the geometry is flat, this becomes project-management software.

04 · The geometry

Three axes, all load-bearing

This is the core of the design. A flat trace viewer is two-dimensional — time and nesting. The third axis is what makes this worth rendering in 3D at all, and it is borrowed from the architecture world we absorbed.

That last point is the whole answer to "there should be no hard page transitions." Waterfall and service map are not separate scenes to cross-fade between. They are the same span geometry, seen from two angles ninety degrees apart. The user drags along that arc and time collapses into topology, or topology unfolds into time.

Why this beats a spline camera path

The common approach is to fly a camera along a pre-authored curve as the user scrolls. It looks cinematic and it means nothing — scroll position maps to an arbitrary point on an arbitrary path.

Here, scroll moves a playhead along the time axis. Spans illuminate as the playhead crosses their start and settle after their end. It is a control engineers already know from every trace viewer and every profiler, it is scrubbable in both directions, and it makes career progression literal instead of implied.

Content gap — blocks §07 Scene 03

The brief asks each project to show Problem · Architecture · Contribution · Challenges · Results. Those four fields do not exist in portfolio.js — a project currently has description, tech, metrics, category.

No amount of geometry substitutes for them. A sub-trace with nothing inside it is an empty room with good lighting. This is the single largest dependency in the plan, and it is content only Akash can supply.

06 · User journey

First load to contact

Load — the trace is already resolved

No boot sequence, no gate, no "press to enter". The waterfall renders complete and legible in the first paint, as semantic HTML. The root span is labelled with the headline answer. A recruiter who never moves the page has still read the thing they came for.

Upgrade — WebGL arrives in place

Once the 2D trace is interactive, the 3D layer loads and takes over the same geometry, animating from the flat layout into depth. If it never arrives — no WebGL, low-power device, a slow network — nothing is missing, because the DOM version is the content.

Scroll — the playhead moves

Time advances from 2020. Spans illuminate as they begin, connections activate, particles start moving along the paths between them. Career progression is watched rather than read.

Hover — the span answers

A span lifts slightly, its attribute chips appear, its parent chain illuminates, and every other span sharing a hovered attribute picks up a rim light. You see what a thing is and what it is related to before committing to a click.

Select an attribute — the hot path

Click PostgreSQL. Every span carrying it illuminates across the whole trace, everything else drops to 8% opacity. This is the "which projects used this" question, answered spatially in one gesture.

Enter a project — descend into a sub-trace

Camera dollies to the span, siblings dim, and the span's internals unfold as a new trace with its own root. Problem, architecture, contribution, results, links. Breadcrumb up in the HUD, Escape to leave.

Orbit — time becomes topology

Drag along the arc. The trace rotates ninety degrees, time foreshortens, and the same spans resolve into the service map. Now the question changes from when to what talks to what. Drag back to return.

Complete — the response returns

The playhead reaches the present. Spans settle, the trace closes, and the response path lights up back toward the client — where contact lives. The end of the request, not a footer.

Direct conflict with your own brief — resolved

The brief asks for a cinematic scroll journey. Your standing rule says a recruiter must understand in thirty seconds. These are in genuine tension, and most 3D portfolios lose the recruiter to the cinema.

The resolution is steps 1 and 2: the trace opens already resolved, and 3D is an upgrade layered onto content that was complete without it. Depth is opt-in. The 3D must never become a toll booth on the content — that principle outranks every effect in §09.

07 · Scene map

One scene, six stations

A note on framing: the brief describes six scenes. Six scenes means six transitions, which contradicts "everything should feel like the same continuous universe." So there is one persistent scene graph holding one dataset, and what changes is camera, filter and level of detail. Nothing is ever torn down and rebuilt.

Station 00
Overview

Three-quarter view, whole trace in frame, playhead at present. The default and the home state. Everything readable, nothing selected.

Station 01
Identity

Playhead at origin. Root span dominant, children collapsed to hairlines. Name, role, thesis. The quietest station.

Station 02
Journey

Waterfall face-on. Playhead scrubs 2020 → present. Roles and milestones resolve as the time cursor crosses them.

Station 03
Ecosystem

Project spans expanded, sub-trace available on select. The deepest station and the one gated on the missing content fields.

Station 04
Attributes

Skills as a filter surface rather than a place. Selecting a tag re-lights the whole trace — the station you can reach from any other.

Station 05
Service map

Orbited ninety degrees. Time collapsed, topology dominant. This is Signal Flow, preserved, now a viewing angle instead of a mode.

08 · Camera & interaction

How the camera and the hands work

Camera states

  • Overview — three-quarter, whole trace framed. Home. Escape always returns here.
  • Waterfall — looking down −Z, near-orthographic so span lengths stay comparable across depth. Time reading.
  • Service map — looking down −X, perspective restored for depth cueing. Topology reading.
  • Span focus — dolly toward one span, siblings dim, children expand.
  • Sub-trace — the selected span becomes the new root; the parent trace remains behind it at low opacity so you never lose your place.

The orbit between Waterfall and Service map is constrained to that 90° arc — you can be anywhere on it, but never off it. That single constraint is what makes free camera control safe: the user can explore without ever getting lost or ending up under the floor.

Input map

  • Scroll / swipe — playhead along time. Never camera dolly; conflating the two is what makes scroll-jacked sites feel broken.
  • Drag / two-finger drag — position on the projection arc.
  • Hover / long-press — span preview, attribute chips, related-span rim light.
  • Click / tap — focus. On an attribute chip, hot-path filter.
  • Pinch / wheel+modifier — zoom, clamped to keep labels legible.
  • Keyboard — ↑↓ siblings, ←→ playhead, Enter descend, Esc ascend, / palette. Full parity, no mouse-only capability.

Motion system

  • Camera — critically damped spring, never a fixed-duration tween. A camera that arrives with a bounce reads as a toy; one that eases to rest reads as an instrument.
  • Spans — staggered by tree depth, not array index. Children resolve after parents, which is causally correct and reads as the system settling rather than a list animating in.
  • Tokens — the existing src/os/motion.js scale carries over unchanged for UI. 3D gets its own spring constants; the two must not be forced to share.
  • Reduced motion — playhead jumps instead of sweeping, camera cuts instead of flying, particles are not rendered. The information is identical; only the transitions go.
09 · Performance

What makes this cheap to render

A trace is the rare visualisation whose natural form is also its fast form. Spans are boxes; boxes instance.

  • One InstancedMesh for every span. 10 projects + 8 timeline entries + repositories + sub-trace children lands around 150–300 instances. Per-instance colour and opacity ride as buffer attributes. This is a single draw call for the entire trace.
  • Edges batched, particles GPU-side. One points system, path progress as an attribute — the technique already working in Signal Flow.
  • Labels are the actual cost, not geometry. Never render 300 labels. Always-on for the ~12 top-level spans, frustum-and-distance culled below that, and a DOM overlay for the focused span only.
  • LOD is semantic. Distant spans collapse into their parent — which is what a trace viewer does anyway when you zoom out. The performance optimisation and the information design are the same mechanism.

Budget

  • R3F currently costs 864 kB raw in this repo. It stays lazy and off the critical path — fetched only after the 2D trace is interactive, or on explicit opt-in over a metered connection.
  • Main bundle must not regress from its current ~272 kB / ~82 kB gzipped.
  • Tier detection via hardwareConcurrency, deviceMemory and a one-second frame probe. Degrade in order: post-processing → particle count → shadows → label count → static.
Cut from the brief — path tracing

Real-time path tracing should be dropped, not tiered. Progressive path tracers accumulate samples over many frames and reset on every camera movement — and camera movement is the entire interaction model here. It would be permanently noisy, precisely while being used.

The quality tiers should govern shading and particle budget, not swap renderers. A second renderer is a second set of materials, lights and bugs for an effect the user cannot see moving.

GitHub API

The current app fetches api.github.com client-side. Unauthenticated that is 60 requests per hour per IP — fine for one visitor, rate-limited under any real traffic, and it puts a network round-trip in the render path of a scene.

Snapshot repositories and commit activity at build time into a committed JSON file; refresh live only as an enhancement after paint.

10 · Mobile

Where this concept pays for itself

A trace waterfall is a vertical list. On a tall screen it is not a degraded desktop view — it is the canonical form of the visualisation.

This is the strongest practical argument for the metaphor. Every other candidate needs a mobile compromise; a city especially, which is unreadable in portrait. Here the phone gets the textbook rendering: spans stacked top to bottom, time running down, depth as indentation. Exactly what Jaeger shows on a narrow viewport, because that is the shape the data wants.

  • No WebGL on phones by default. The DOM trace is the real thing, not a fallback — same dataset, same IA, same interactions, zero of the 864 kB.
  • Swipe drives the playhead. Tap focuses a span. Tap an attribute runs the same hot-path filter as desktop.
  • The service map is the flat SVG topology already shipped on the phone — which is exactly camera B's projection, drawn in 2D. The two views the desktop reaches by orbiting, mobile reaches by a toggle.
  • 3D remains reachable on capable phones behind an explicit opt-in that names the cost.
11 · Component architecture

Five layers, one direction of dependency

src/trace/
├─ data/            content engine — pure, no React, no THREE
│   ├─ trace.js       builds the span tree from portfolio + posts + gh snapshot
│   ├─ attributes.js  tech → attribute index, powers the hot path
│   └─ layout.js      span → (x,y,z); the only place geometry is decided
│
├─ state/           interaction engine — no THREE
│   ├─ useTrace.js    playhead, focus, filter, projection, breadcrumb
│   └─ input.js       scroll / pointer / touch / key → intent
│
├─ scene/           3D engine — imports data + state, never the reverse
│   ├─ SpanField.jsx  one InstancedMesh for all spans
│   ├─ EdgeField.jsx  ·  ParticleField.jsx
│   ├─ CameraRig.jsx  the constrained 90° arc lives here
│   └─ Effects.jsx    tier-gated post-processing
│
├─ dom/             the semantic trace — always rendered, always first
│   └─ Waterfall.jsx  real HTML tree; mobile, no-WebGL and screen readers
│
└─ ui/              presentation — HUD, breadcrumb, inspector, palette

The rule that keeps content decoupled from the scene: scene/ may import from data/ and state/; neither may import from scene/. Adding a project adds a span, and the geometry follows from layout.js with no scene edit — which is the data-driven requirement, enforced by dependency direction rather than by discipline.

One consequence worth stating plainly: dom/Waterfall.jsx is not a fallback. It is the primary rendering, it ships first, and WebGL is an enhancement layered over it. That single decision satisfies the accessibility requirement, the no-WebGL requirement, the mobile requirement and "no information may exist only inside WebGL" — with one mechanism instead of four parallel implementations that drift apart.

12 · Migration

What survives, and one decision for you

The brief says to retire the fake macOS. Agreed — but the costume and the machinery are different things, and only one of them should go.

Retired
The macOS costume

Traffic lights, menu bar, dock magnification, the desktop-and-wallpaper frame. This is what makes it read as an imitation rather than a product — including the dock work shipped this week.

Kept whole
The machinery

Window manager, command palette, keyboard shortcuts, settings, notifications, boot. Weeks of real work, none of it macOS-specific. The palette becomes the primary navigation the brief asks for.

Promoted
Signal Flow

Becomes camera B of the trace rather than a separate mode. src/flow/graph.js survives largely intact as the Z-axis source.

Kept
Everything content

portfolio.js, posts.js, the mobile flow map, Figures, PostBody, the CSP and headers. The content engine is already data-driven and is what the trace is built from.

The decision I need from you

The brief reads as Trace replaces everything. I'd argue for one variation: Trace becomes the front door and the primary navigation, and the windowed workspace survives underneath as the reference surface.

The reasoning is that these are two different jobs. A trace is a narrative surface — superb for a first-time visitor, a recruiter, a story. A windowed workspace is a reference surface — superb for someone who wants to open four projects side by side and keep a terminal running. Killing it throws away the depth that makes a developer stay past ten minutes.

Either way the macOS costume goes and Trace is the shell. Say which and I'll build to it.

13 · Blocking

What has to exist before this can be built

  • Project case-study fields. Problem, architecture, contribution, challenges, results — for at least the 3 flagship projects. Station 03 is the deepest part of the experience and it is empty without them. This has now come up three times; it is the real critical path.
  • Milestone dates. The time axis needs start and end per role and per project. timeline[] has years; spans need enough granularity to have length, not just position.
  • The migration decision in §12.
  • A GitHub snapshot step in the build, replacing the live client fetch.

Nothing else blocks. The geometry, the camera, the layout function and the DOM waterfall can all be built against the data that exists today, and will light up as the content lands.
